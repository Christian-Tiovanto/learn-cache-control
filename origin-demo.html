Browser cache test: straight to the origin

This page is served by server.js itself. By default every fetch() goes directly to the origin with no proxy or CDN, so only your browser's own cache is in play. Switch Send requests to to the nginx proxy and the answer can also come from nginx's cache. The tables show what the browser received, and what the origin actually saw.

Use a single tab, and keep DevTools "Disable cache" unticked, or the browser cache never answers.

The proxy is on another port, so this is a cross-origin request: nginx must send CORS headers (already in nginx.docker.conf). Keep opening this page as http://localhost:3000/demo.
Always "Browser cache"? The response says max-age=60, so your browser caches it too and never asks nginx. Click cache: "reload" or "no-store" to skip the browser's copy, or start the server with cache-config.nginx-only.json (see README) so only nginx caches.

The header is only visible to the server if a request leaves the browser. Chromium browsers (Chrome, Edge, Brave) act on exactly max-age=0 and no-cache and then skip or validate their stored copy. A number like max-age=6 is still sent when a request goes out, but your browser's own cache does not use it to decide: a fresh copy is simply replayed, no request is made, and the header never reaches the server. Request max-age=N works against caches that implement it (see cache-proxy.js).

What to expect (assuming the default values in cache-config.json)
  • /api/products: click default twice. The 2nd click is answered by the browser cache and the origin table gets no new line. no-cache forces a request: the origin sees max-age=0 and If-None-Match, and the body changes, so it answers 200.
  • /api/user/profile: private is fine for a browser, so it is cached for 5 minutes like products.
  • /api/inventory: max-age=0, must-revalidate plus an ETag. Every click reaches the origin. After the first, the origin answers 304 while the stock is unchanged. The page still sees status 200, because the browser reuses its stored body. Click Sell 1 widget and the next request becomes a 200 with new data.
  • /api/user/payment-methods: no-store, so every click reaches the origin.
  • /api/trending (stale-while-revalidate): within 60 s it is a cache hit. After 60 s a browser that supports the directive serves the old copy and refreshes in the background. But per Chromium developers, Chrome applied it only to subresources and not to fetch() calls (an older discussion, so verify). Watch the origin table to see what really happens.
  • /api/status (stale-if-error): turn Outage ON after the 5 minutes pass and request again. Browsers generally don't implement stale-if-error, so expect the 503 to reach the page. A proxy or CDN is where it works.
  • Via the nginx proxy: click default twice on /api/products. 1st: nginx asks the origin (MISS). 2nd: the browser answers. Now use reload: the browser skips its copy, nginx answers HIT and the origin table stays quiet. nginx ignores a client no-cache by default (see "nginx received request Cache-Control").
  • Edited cache-config.json? Only new responses carry the new headers. A copy your browser already stored keeps the freshness it was given, so fetch it again with cache: "reload" (or clear the cache) before judging the change.
  • Waiting is real here. Start the origin with TTL_DIVISOR=30 to shrink every lifetime 30x.
